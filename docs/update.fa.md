# آپدیت با یک دستور

روی همان سروری که OpenVPNPA نصب شده است اجرا کنید:

```sh
curl -fsSL https://raw.githubusercontent.com/zhilvanzhinos/openvpnpa/main/update.sh | sudo bash
```

این دستور در هر اجرا آخرین commit شاخه **main** را می‌گیرد؛ به نسخه ثابت نصب
اولیه محدود نیست. در نصب کامل، نام کاربری، رمز، توکن، تنظیمات پورت و گواهی دوباره پرسیده
نمی‌شوند. اگر Docker، Compose یا ابزار لازم در دسترس نباشد، پیش‌نیازها
خودکار آماده می‌شوند. اگر نصب اولیه یا ساخت کانتینر نیمه‌تمام باشد، نصب‌کننده
آن را ادامه می‌دهد و فقط اطلاعاتی را می‌پرسد که هنوز ذخیره نشده‌اند. پس از اولین آپدیت موفق، دستور محلی هم ساخته می‌شود:

```sh
sudo /opt/openvpnpa/update
```

هر دو فرمان ابتدا کد تازه را از GitHub دریافت می‌کنند. اگر همان commit سالم
در حال اجرا باشد، سرویس بی‌دلیل restart نمی‌شود. پیام‌های ترمینال فینگلیش‌اند.

## روند اجرا و حفظ اطلاعات

* نصب قبلی از labelهای کانتینر پروژه `openvpnpa` و مسیرهای mount بررسی می‌شود.
  این ابزار برای نصب استاندارد در `/opt/openvpnpa` است؛ نصب سفارشی با override
  ناشناخته متوقف می‌شود تا تنظیمات آن بازنویسی نشود.
* checkoutهای قبلی حفظ می‌شوند. هر commit در پوشه مستقل
  `/opt/openvpnpa/releases/git-COMMIT` قرار می‌گیرد؛ فایل‌های قبلی reset یا حذف نمی‌شوند.
* تصویر جدید با tag همان commit ساخته می‌شود، در حالی که سرویس قبلی هنوز
  در حال اجراست. شکست build سرویس قبلی را متوقف نمی‌کند.
* برای جایگزینی، فقط سرویس `node` همین پروژه به‌آرامی متوقف می‌شود. این مرحله
  اتصال‌های OpenVPN را کوتاه‌مدت قطع می‌کند؛ کلاینت‌ها باید دوباره وصل شوند.
* پس از توقف، از config و state در
  `/opt/openvpnpa/backups/TIMESTAMP/config-state.tar.gz` پشتیبان گرفته می‌شود.
  آرشیو شامل اطلاعات خصوصی است و با دسترسی 0600 در پوشه 0700 نگهداری می‌شود.
* تصویر جدید با همان config و state راه‌اندازی و سلامت آن بررسی می‌شود. API Key،
  Certificate، کلیدهای کاربران، نگاشت UID، دفتر مصرف و انتخاب گروه‌ها حفظ می‌شوند.
* دستور `/opt/openvpnpa/manage` برای مدیریت نسخه جدید به‌روز می‌شود. helperهای
  سفارشی حفظ می‌شوند و در صورت لزوم نام جایگزین در خروجی اعلام می‌شود.

پنل اصلی PasarGuard، دیتابیس آن، نود V2Ray فعلی و فایروال میزبان توسط
این دستور تغییر داده نمی‌شوند. daemon فعال Docker restart نمی‌شود؛ Docker
جدید در صورت نبودن نصب می‌شود و daemon محلی متوقف در صورت نیاز start می‌شود.
اگر daemon فعال باشد ولی CLI در دسترس نباشد، برای جلوگیری از تعویض engine
موجود عملیات متوقف می‌شود. هیچ `docker prune`، حذف volume یا
تعویض مجموع مصرف انجام نمی‌شود. اجرای هم‌زمان دو آپدیت با lock متوقف می‌شود.

## خطا و بازگشت

اگر نسخه جدید سالم نشود، تصویر دقیق قبلی و Compose قبلی دوباره راه‌اندازی
می‌شوند. دفتر مصرف زنده از backup بازگردانی نمی‌شود؛ بازگردانی خودکار می‌تواند
مصرفی را که نسخه جدید در فاصله کوتاه اجرا ثبت کرده از بین ببرد.

اگر نسخه جدید در آینده migration ناسازگار روی داده محلی انجام دهد، برگشت
تصویر به‌تنهایی ممکن است کافی نباشد. در صورت شکست rollback، ابزار مسیر backup
را اعلام می‌کند و state را دست‌نخورده می‌گذارد تا بازیابی آگاهانه انجام شود.
بازگردانی دستی archive نیز باید در توقف سرویس و با درنظرگرفتن مصرف جدید باشد.

فایل `/opt/openvpnpa/last-update.json` commit و مسیر backup آخرین آپدیت موفق
را نگه می‌دارد. backupها و تصویرهای rollback خودکار پاک نمی‌شوند؛ فضای دیسک
باید برای نگهداری آن‌ها کافی باشد. برای آپدیت‌های بعد از دستور update استفاده
کنید، نه اجرای دوباره install نسخه ثابت.

## شواهد آزمایش

تست‌های مستقل شکست build، موفقیت، عدم restart برای commit یکسان، حفظ داده و
helper سفارشی، شکست health، شکست rollback و شکست نوشتن metadata اجرا می‌شوند:

```sh
python -m unittest tests.test_update -v
```

آزمایش Docker واقعی با پروژه تصادفی جدا و کانتینر نمونه، جایگزینی، عدم تغییر
commit یکسان و برگشت از نسخه ناسالم به **همان image قبلی** را بررسی می‌کند:

```sh
python -m scripts.check_update
```

این آزمایش به پنل فعال متصل نمی‌شود، پورت عمومی باز نمی‌کند و VPN ایجاد
نمی‌کند. تأیید مسیر update جای آزمون تونل واقعی و سازگاری نسخه فعال پاسارگارد
را نمی‌گیرد؛ محدودیت‌های ثبت مصرف پروتکل اصلی همچنان برقرارند.
